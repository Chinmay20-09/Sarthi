# dev/ — Developer documentation

This is the permanent technical source of truth for Sarthi. It describes the
system **as implemented** — the repository code is the implementation source
of truth, and these documents are kept aligned with it.

## Documents

| Document | Question it answers |
| --- | --- |
| [ARCHITECTURE.md](ARCHITECTURE.md) | *How does Sarthi work?* System architecture, runtime flow, module responsibilities, skills/tools/agents, knowledge, memory, database, hands/IPC, chaining, browser automation, API, data flow, configuration, dependencies, CLI |
| [PROJECT_STATE.md](PROJECT_STATE.md) | *What is its current state?* Implemented / partial / planned, known limitations, current architectural issues, unfinished work. **Read this before deciding what to work on next.** |
| [DEVELOPMENT.md](DEVELOPMENT.md) | *How do I work on it?* Development setup, repository layout, commands, adding skills, backend/client conventions, critical workflows |
| [TESTING.md](TESTING.md) | *How is it tested?* How to run tests, what is covered, what is NOT covered, manual validation requirements |

## Documentation philosophy

- **Code is the source of truth.** A claim is only documented when a file
  path backs it. Never describe planned architecture as implemented.
- **Consolidation over fragmentation.** Prefer one good document with clear
  sections over several small overlapping ones. Do not create new permanent
  documents without a strong demonstrated need.
- **Every layer serves one question:**
  - `docs/client/` → How do I *use* Sarthi?
  - `docs/dev/` → How does Sarthi *work* and what is its current state?
  - `docs/agent/` → What does the coding agent need to know *right now*?
  - `docs/archive/` → What happened *previously*?
- **Historical material belongs in `docs/archive/`.** Superseded documents are
  archived, never edited in place. The current archive root is
  [`docs/archive/documentation-reset-2026-09/`](../archive/documentation-reset-2026-09/),
  which holds the pre-2026-09-16 documentation system: the forensic audit
  (divergence matrix, dead-code and duplication reports, consolidation
  plan/report), the full architectural decision log (AD-01…AD-16), and the
  former per-topic documents this folder was consolidated from.

## Conventions for editing these documents

- When code changes, update the describing section in the same change —
  do not leave stale architecture in `ARCHITECTURE.md`.
- Inventories (endpoints, skills, tools, tables) must be regenerated by
  inspection, not edited from memory.
- Distinguish IMPLEMENTED / PARTIAL / PLANNED explicitly. State unknowns as
  unknowns; never invent certainty.
- Sprint-context documents for coding agents live in `docs/agent/` — that is
  a temporary context package, not part of this permanent documentation.
